## Decisions changed

### Q1 — embedder: EdgeFace → **SFace** (reversed)

EdgeFace's GitHub repo is BSD-3 **and the weights are committed inside it**, which looks
conclusive. It is not. The authors also publish those weights on HuggingFace under
**`cc-by-nc-sa-4.0`**, declared in the model card frontmatter, across all four official
`Idiap/EdgeFace-*` repos. NonCommercial fails DFSG §6 → Debian cannot ship it → blocked
by Q6.

Consistent with the model card stating training on **WebFace260M** (research-only).
Same shape as InsightFace, which was already ruled out for the same reason.

Cost: 512-d → 128-d, ~7 MB → 37 MB, and ~10–15 ms projected → **85 ms measured**.
The embedder trait made it a config change rather than a rewrite.

### Q2 — runtime: **`tract`** (decided)

Both load and run YuNet + SFace and both meet the latency target, so this was decided on
footprint and attack surface. `tract` takes 318 ms vs `ort`'s 200 ms, and gives up int8,
in exchange for **zero native dependencies** — the built binary links only
`libc`/`libm`/`libgcc_s` — and a ~62 MB install against ~134 MB.

`ort` and its 8 packages were removed from the spike and from the system afterwards.
Full table in [wiki/08 Q2](../../wiki/08-open-questions.md#q2--inference-runtime--decided-tract).

### Device resolution: `by-id` → **`by-path`**

`by-id` produces two symlinks for four nodes on this hardware and **neither resolves to
the IR camera** — both UVC interfaces share serial `SN0001`, so the name collides and the
survivor points at the RGB camera.

## Measurements

### Corpus — dark-frame integrity **verified**

```
RECORDING                          median       MAX(OFF/ON)   verdict@1e-3
attack_floodlight_remote         7.18e-02        1.30e-01         REJECT
null_empty_room                  1.00e-05        1.54e-05          allow
live_dark_frontal                3.21e-06        5.36e-06          allow
```

Four orders of magnitude between worst honest capture and the attack. **Zero false
rejections across 210 live pairs.** Threshold `max(OFF/ON) > 1e-3` sits ~65× above the
worst live reading and ~130× below the attack.

## Bugs found (full write-ups in [wiki/11](../../wiki/11-bug-log.md))

| # | Bug | Severity |
|---|---|---|
| B11 | Benchmarked `tract` against a published figure from **another machine** | medium |
| B10 | EdgeFace **weights** CC BY-NC-SA, not BSD-3 | **critical** |
| B9 | Dark-frame check defeated by a **pulsed** IR source at per-pair granularity | **critical** |
| B8 | Liveness cannot run before detection, but the pipeline said it does | high |
| B7 | Centre-crop ROI is not on the face → falloff unmeasurable | high |
| B6 | `by-id` resolves to the wrong camera | high |
| B5 | ffmpeg silently duplicates frames when writing to disk | high |
| B4 | Capture with no sidecar joins the corpus undocumented | medium |
| B3 | `2>/dev/null` hid a missing binary as "no evidence" | medium |
| B2 | Half the `/dev/videoN` nodes are not cameras | low |
| B1 | Dead conditional in `build_pairs` | trivial |

The three that changed the design:

- **B9** — an IR remote pulses, so 7 of 42 attack pairs (16.7%) read as perfectly clean.
  At the 2-pair capture budget that is a **1-in-36 bypass**. The motion-consistency check
  did *not* fix it (CV 0.54 for the attack vs 0.33–0.65 for live — no separation, because
  sensor read noise is relatively noisy). What fixed it: **conjunctive aggregation** —
  liveness requires *every* pair to pass, while matching stays k-of-n. Opposite rules,
  must never be unified.
- **B8/B7** — the falloff test is defined over "the detected face region" but the pipeline
  put liveness entirely before detection. Contradiction. Detection moves earlier, and
  YuNet becomes a **prerequisite for finishing S5** rather than a later step.
- **B10** — see above.

## Corrections made to my own earlier statements

Both were stated to the user before being caught, and both changed a conclusion:

1. **"BSD-3 covers the EdgeFace weights — yes."** Wrong; checked only the GitHub repo.
   The weights are CC BY-NC-SA at their distribution point.
2. **"`tract` is within ~5% of the C++ reference per pixel."** Wrong; compared `tract` on
   this laptop against OpenCV's published benchmark from unknown hardware. Same-machine,
   `ort` is 3–20× faster. Also attributed "non-square fails" to `tract` before testing
   `ort`, which fails identically — it is a YuNet model limitation.

Both share a root cause: **a conclusion drawn from one side of a comparison.** Logged as
B11 for the reusable lesson.
